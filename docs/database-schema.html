CineTrack · schéma SQLite

Comment CineTrack range vos films et séries

La base est du SQLite local, embarqué dans l'app via Tauri — pas de serveur, tout vit sur le poste. Elle est pensée multi-profils dès le départ : presque chaque table porte un profile_id qui isole les données d'un profil des autres, avec des contraintes FOREIGN KEY … ON DELETE CASCADE qui garantissent qu'aucune ligne ne survit à la suppression de son profil ou de sa liste. Depuis peu, chaque profil est en plus lié à un compte Supabase — y accéder nécessite d'être connecté avec ce compte précis.

Profils & préférences

2 tables

Le socle de tout le reste : chaque profil a sa propre bibliothèque, son historique, ses listes. Les préférences, elles, ne suivent volontairement pas ce découpage.

profiles racine

Un profil = une personne qui utilise l'app. Toutes les tables ci-dessous s'y rattachent par profile_id. Le profil 'default' est créé automatiquement à la première migration et ne peut jamais être supprimé. Depuis la migration 008, un profil doit être lié à un compte Supabase pour être accessible : le premier compte qui se connecte réclame automatiquement 'default' (et ses données existantes), tout compte suivant doit créer son propre profil.

Colonne Type Détail
PKid TEXT identifiant du profil ('default' ou UUID)
name TEXT nom affiché
avatar TEXT optionnel
created_at TEXT date ISO
supabase_user_id TEXT optionnel, unique — id du compte Supabase lié ; pas de FK possible, auth.users vit chez Supabase, hors de ce fichier SQLite
preferences clé / valeur

Réglages de l'application : thème, couleur d'accent, langue, région TMDB, spoiler protection, notifications, et activeProfileId — le profil actuellement sélectionné. C'est une table globale, partagée par tous les profils : ils partagent la même app, pas les mêmes préférences par profil.

Colonne Type Détail
PKkey TEXT ex. theme, activeProfileId
value TEXT valeur encodée en JSON
Aucune relation déclarée — table intentionnellement indépendante des profils.

Bibliothèque & progression

6 tables

Le cœur fonctionnel de l'app. Trois idées coexistent volontairement : un état courant (library_items, status), un journal d'événements immuable (viewing_events, utilisé pour les statistiques) et des tables de suivi plus légères héritées des premières versions (watchlist, seen, progression d'épisodes).

library_items fiche de suivi

La fiche complète d'un film ou d'une série dans la bibliothèque d'un profil : son statut (planned, watching, paused, completed, dropped, rewatching), la note personnelle, des notes libres, des tags, les dates de début/fin et le nombre de re-visionnages.

Colonne Type Détail
PKFKprofile_id TEXT → profiles.id
PKmedia_id, media_type INT, TEXT identifiant TMDB + movie/series
status TEXT défaut planned
favourite, user_rating, notes, tags … tags en JSON
genres TEXT JSON, copié depuis TMDB
started_at, completed_at, rewatch_count … renseignés selon les changements de statut
Un profil possède 0..n entrées de bibliothèque. Supprimer le profil supprime la ligne (ON DELETE CASCADE).
viewing_events journal (append-only)

Chaque visionnage (ou annulation) génère une ligne ici : film entier ou épisode précis, avec sa durée. C'est cette table — pas library_items.status — qui alimente les statistiques (minutes vues, séries de jours consécutifs, activité mensuelle).

Colonne Type Détail
PKid TEXT UUID
FKprofile_id TEXT → profiles.id
event_type TEXT watched / unwatched / rewatched
watched_at, duration_minutes TEXT, INT horodatage + durée pour les stats
episode_id, season_number, episode_number INT nuls pour un film
Un profil journalise 0..n événements.
profile_watchlist à voir

La liste « à regarder » simple — plus légère que library_items, sans statut ni note.

Colonne Type Détail
PKFKprofile_id, media_id, media_type … clé composite
title, poster_path, backdrop_path, year, rating … copie TMDB au moment de l'ajout
Un profil a 0..n entrées à voir.
profile_seen_movies vu / pas vu

Un simple bascule « vu » pour les films, plus rapide que de passer par la bibliothèque complète.

Colonne Type Détail
PKFKprofile_id, movie_id … clé composite
watched_at TEXT date du visionnage
Un profil a 0..n films marqués vus.
profile_episode_progress progression

Une ligne par épisode regardé. C'est la source de vérité pour savoir où en est un profil dans une série — le décompte affiché est recalculé à la lecture, pas stocké.

Colonne Type Détail
PKFKprofile_id, series_id, episode_id … clé composite
season_number, episode_number INT repère l'épisode
watched, watched_at BOOL, TEXT
Un profil a 0..n épisodes marqués vus.
profile_tracked_series séries suivies

Une ligne par série qu'un profil suit activement. Le nombre d'épisodes vus n'est pas stocké ici : il est calculé par une jointure avec profile_episode_progress à chaque lecture, pour ne jamais désynchroniser un compteur.

Colonne Type Détail
PKFKprofile_id, series_id … clé composite
total_episodes INT total connu côté TMDB
updated_at TEXT
Un profil suit 0..n séries.

Historique d'activité

1 table

Le fil d'activité affiché à l'écran « Historique » — lisible par un humain, distinct du journal statistique ci-dessus même si les deux s'écrivent souvent au même moment.

activity_log fil d'activité

Chaque action notable — ajout à une liste, film marqué vu, épisode ou saison entière cochée — devient une ligne ici avec un action parmi 13 valeurs possibles (movie:watched, watchlist:add, list:remove…) et un champ metadata en JSON pour les détails propres à chaque action.

Colonne Type Détail
PKid TEXT UUID
FKprofile_id TEXT → profiles.id, nullable
action TEXT ex. episode:watched
season_number, episode_number, episode_title … renseignés pour les épisodes
metadata TEXT JSON libre
timestamp TEXT indexé pour un tri rapide
Un profil a 0..n lignes d'historique.

Disponibilité streaming

2 tables

« Que regarder ce soir » et les alertes de disponibilité s'appuient sur ces deux tables — l'une appartient à un profil, l'autre décrit un fait sur un titre, partagé par tous.

availability_alerts abonnement

« Préviens-moi si ce film devient disponible sur telle plateforme » — un profil peut s'abonner à un titre pour une région et une liste de plateformes préférées.

Colonne Type Détail
PKid TEXT UUID
FKprofile_id TEXT → profiles.id
region, provider_ids TEXT provider_ids en JSON
enabled BOOL défaut vrai
Un profil crée 0..n alertes.
availability_snapshots fait partagé

Le dernier relevé connu des plateformes proposant un titre, par région — une propriété du titre, pas d'un profil, donc partagée par tous. Rapprochée des alertes en mémoire par l'app (pas de clé étrangère entre les deux), pour détecter une nouvelle disponibilité.

Colonne Type Détail
PKmedia_id, media_type, region … clé composite

Modèle conceptuel (MCD)

schéma actif uniquement

Les entités et leurs cardinalités — les colonnes complètes sont dans les fiches ci-dessus, ici on ne garde que ce qui identifie chaque ligne. Les tables historiques n'y figurent pas : elles ne participent plus au modèle vivant de l'app.

Lecture des cardinalités : ||—o{ se lit « un, obligatoirement » du côté du trait double, « zéro à plusieurs » du côté du trait ouvert. Exemple — PROFILES ||--o{ LIBRARY_ITEMS : un profil a zéro à plusieurs fiches de bibliothèque, une fiche appartient à exactement un profil.

entités reliées à profiles par une vraie contrainte FK PREFERENCES et AVAILABILITY_SNAPSHOTS : volontairement isolées, pas de FK

PROFILES.supabase_user_id (UK = unique key) n'a volontairement aucune ligne de relation dans ce diagramme : son "parent" conceptuel, auth.users, vit dans la base Postgres de Supabase — un fichier SQLite séparé ne peut ni le référencer ni le joindre. C'est une donnée de corrélation, pas une contrainte imposée par le moteur.

Les 9 relations vers profiles et celle de custom_list_items vers custom_lists sont posées en ON DELETE CASCADE depuis la migration 007 — supprimer un profil ou une liste supprime tout ce qui lui appartient, jusqu'au bout de la chaîne. La migration 008 ajoute le lien profiles.supabase_user_id qui conditionne l'accès à un profil à une connexion Supabase.
